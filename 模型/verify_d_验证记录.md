## 1. 假设检验：水率 → T3 到底是什么关系

### 1.1 事件研究：升级后仍是「伪影」

README 3.1 节已自我质疑"反向期疑似辨识伪影"。本次用趋势校正复检 12 个干净阶跃：

| 方法 | 0~5min | 5~15min | 15~30min | 30~60min |
|---|---|---|---|---|
| 原始·升水组 | +6.81 | +5.18 | −2.54 | −0.90 |
| 原始·降水组 | +5.16 | +5.93 | −4.07 | −4.01 |
| 趋势校正·升水组 | +6.52 | +4.17 | −4.75 | −5.28 |
| 趋势校正·降水组 | +5.28 | +6.37 | −3.12 | −2.12 |
| 原始·合并 | +6.12 | +5.49 | −3.17 | −2.19 |
| 趋势校正·合并 | +6.01 | +5.08 | −4.07 | −3.96 |

**关键读法：升水组和降水组在 0~15min 窗口符号相同（都是正）。**
若真是"水率驱动温度"，升水与降水的早期响应必须反号。
两组同号只能说明：这 12 个事件的共同特征是"事件前温度在动"，
事件研究测到的是**趋势延续**，不是水率效应。趋势校正没救回来，因为
事件前 15min 的线性斜率不足以描述操作员的反应形状。

### 1.2 滞后互相关：把因果与反馈分开（决定性证据）

班次内去均值 + 去线性趋势 + 归一化，7 个有变化的班次平均：

```
lag<0 = T3 先变、操作员后调水（反馈）；lag>0 = 水率先变（因果）
-40:-0.11  -20:+0.13  -10:+0.34  -5:+0.44  +0:+0.45
+5:+0.30  +10:+0.04  +15:-0.29  +20:-0.51  +30:-0.44  +40:-0.30
```

两个峰，必须分开读：

- **lag = −5min, corr = +0.44**：T3 先升，5 分钟后操作员加水。
  这是**反馈**。它就是 G_OLD 那个 +0.47 早期正向峰的来源。
- **lag = +20min, corr = −0.51**：水率先加，20 分钟后 T3 降。
  这是**真实的冷却因果**，幅度比反馈项更大。

结论：**"加水降温"是真的，"先升后降"的"先升"是反馈伪影。**
响应核 G_OLD 前半段（0~15min 正峰）在物理上是错的，
它把"操作员看到升温才加水"误编码成"加水会导致升温"。

### 1.3 静态回归：符号相反

| 方法 | 增益 | R² | 说明 |
|---|---|---|---|
| 全段混合回归 | **+0.1228** ℃/(L/t) | 0.084 | 被班次间批次差异污染 |
| 班次内去均值 | **+0.1647** ℃/(L/t) | 0.202 | 已剥离批次，**仍是正号** |
| 模型设定 | −0.151 | — | 符号相反 |

班次内去均值后仍为正，是因为闭环保留下式：
$T3$ 与 $u$ 同时受反馈项和因果项影响，OLS 估的是两者混合。
所以**回归系数不能用来标定增益**，只有滞后互相关能分离。
这一点 README 3.2 节说的"同步回归斜率 −0.273"也存在同样问题，
那次是负号纯属班次构成不同，不是更可信。

**电流高高报 0、给料越界 0、T3 硬边界 0。**

3 次"水率越界"全部定位到同一形态：班次第 0 拍处于启动阶段，
模型按设计「保持现场初始设定」，而现场初始水率写成 300，

现场确实会用 300 开工（10-14 / 10-15 / 10-17 三个班次都这样），
所以要么把启动阶段的裁剪放宽到文档给定下限 200，
要么把 `ratio_safe_min` 降到 300。当前状态是自相矛盾的。

> 本层只验合规，**不能作为控制能力证据**。

## 3. 反事实闭环：控制效果

自持水率（不读人工历史）+ 共同扰动 `d` + 响应核推演 T3。7 个有效班次，2129 分钟。

### 3.1 主结果

| 班次 | min | 人工 | 模型(快开) | 模型(快关) | 恒定最优 |
|---|---|---|---|---|---|
| 10-12 22:34 | 201 | 100.0% | 100.0% | 100.0% | 640 / 100% |
| 10-15 00:16 | 432 | 54.9% | **44.9%** | 53.9% | 640 / 51% |
| 10-15 16:57 | 127 | 100.0% | 100.0% | 100.0% | 620 / 100% |
| 10-16 00:04 | 420 | 100.0% | 100.0% | 100.0% | 640 / 100% |
| 10-16 23:53 | 230 | 100.0% | 100.0% | 100.0% | 600 / 100% |
| 10-18 00:05 | 374 | 51.6% | 60.4% | 58.3% | 620 / 52% |
| 10-18 21:19 | 345 | 69.9% | 78.0% | 77.1% | 700 / 79% |
| **加权** | **2129** | **77.5%** | **78.3%** | **79.6%** | **78.1%** |

三个必须同时说的数字：
- 模型(快关) 比人工 **+2.1pp**
- 模型(快关) 比恒定水率最优 **+1.4pp**
- 但恒定最优本身就有 78.1%，**模型的全部价值只有 1.4pp**

而在 2129 分钟样本上，1.4pp ≈ 30 分钟合格时间差。
这个量级在模型内自证的前提下，**不足以支撑"模型有效"的结论**。
只能支撑一个更弱的结论：**模型没有比"不动"更差，且在有考题的班次略好**。

### 3.2 病灶：在 2 个"有考题"的班次上，模型把水率顶到上限

| 班次 | 水率顶格 690 的占比 | 水率均值 | 降料次数 |
|---|---|---|---|
| 10-15 00:16 | **78.9%** | 678 | 3 |
| 10-18 00:05 | **57.0%** | 664 | 3 |
| 10-18 21:19 | **96.8%** | 690 | 3 |

三个 T3 高温班次里，模型有 57~97% 的时间把水率钉在操作上限，
降料 3 次（顶到 `lime_band` 下限 3.00），仍压不住，然后什么都不做了。

这与 README 3.2b 节记录的初版失败模式**同形**：
"模型在拼命纠一个它纠不动的量"，25 次动作里有 12 次是降料。
区别是现在有 35min 节拍限制，所以退化得没那么难看。

10-15 00:16 班的完整动作链（前 60 分钟）：

```
+ 0min 保持  -> 600  T3=115.8 在带内
+30min 加水  -> 625  快通道 瞬时T3=136.2
+40min 加水  -> 690  快通道 瞬时T3=146.6（一步 +66）
+50min 降料  -> 690  水率已到上限仍 T3=152.3
+60min 减水  -> 656  快通道(严重低温) 瞬时T3=91.4  ← 30 分钟内从 152 打到 91
```

**152 → 91 只用了 10 分钟。** 这不是物理，是响应核在自激：
G_OLD 说"加水会先升温"，所以 40min 那步 +66 L/t 在模型内被推演成
T3 冲到 152，下一拍立刻判定"严重超温"，再下一拍判定"严重低温"。

### 3.3 换核实验：把响应核换成物理纯滞后核，成绩全面提升

`G_PURE` = 10min 输运死时间 + 8min 一阶惯性，稳态 −0.15 ℃/(L/t)，
**唯一差别是去掉 G_OLD 的早期正向峰**。

| 变体 | 加权合格率 |
|---|---|
| G_OLD 快通道开（现状） | 78.3% |
| G_OLD 快通道关 | 79.6% |
| **G_PURE 快通道开** | **81.5%** |
| G_PURE 快通道关 | 80.0% |

两个结论：

1. **G_OLD 的早期正向峰在拖累控制器**（81.5% vs 78.3%，+3.2pp）。
   这与 1.2 节滞后互相关的诊断完全一致：那个峰是反馈伪影。
2. **快通道本身是对的，但只在核正确时才对**：
   - 配 G_OLD：快开 78.3% < 快关 79.6%（**−1.3pp**）
   - 配 G_PURE：快开 81.5% > 快关 80.0%（**+1.5pp**）
   逐班次看更清楚，10-15 00:16 班：G_OLD 快开 44.9% / 快关 53.9%（−9.0pp），
   G_PURE 快开 62.3% / 快关 56.5%（+5.8pp）。

**交互解释**：快通道是"一步顶格"（15~90 L/t 单步）。
核说加水先升温 → 大步 → 模型内立刻超温 → 反向操作 → 震荡。
核说加水单调降温 → 大步 → 持续降温 → 正确。**步长越大，核的符号错误越致命。**

## 4. 工况对照：模型管不到的工艺需求

《预期实现效果.txt》原文：「二级消化器温度须高于 1、3 级」；
《模型参数.txt》第 16 项：「消化桶中 2 级消化器温度须高于 1、3 级，从而保证大量反应在二级」。

实测（生产 3079 min）：

| 指标 | 值 |
|---|---|
| 层级均值 | T1 **151.6** / T2 121.7 / T3 119.5 |
| T2 > T1 占比 | **14.8%** |
| T2 > T3 占比 | 28.5% |
| **T2 同时最高** | **14.5%** |

**工艺要求的"T2 最高"在这批数据里基本没实现。**
T1 均值 151.6 远高于 T2/T3，其中 T1-WDZ1 单点均值 201.7。

这意味着：
- 「优先保证二级温度处于最高运行状态」这条需求，模型**完全没有对应控制逻辑**
  （controller.py 里 t2 只用于快照输出，不参与任何决策）
- 若这条需求是真需求，当前模型缺一整个目标维度
- 若不是真需求（比如 T1 那个 201.7 是测点位置问题），则需求文档需更正

**这是本次验证里唯一"模型管不到"的实质缺口，需要现场确认。**

两个问题叠加：

1. **4 个班次均值 ≈ 4.0**，正好等于模型允许的**上边界**。模型无法把给料
   提到现场实际水平以上。
2. **实测 P95 达 4.36~4.63，最大 4.85~5.27**，全部超出模型上限 4.00。
   模型若接管，这 8 个班次的给料全部被压在 4.0 以下。

而现场实际在 4.0 运行 —— **模型把产量砍了 12.5~25% 去换温度**，
这个代价从未被评估过。

⚠️ 更要紧的是：`lime_field_sp` 是**现场设定值**，本该每班次读取后
经 `/reset` 传入。当前默认 3.5 只是个占位值，但它已经写死进了
Python 默认参数，如果服务启动时没人 `/reset`，模型就按 3.5 跑。
数据里也不存在 `SSHLLSDZ`（生石灰流量设定值）测点，
说明这个值只能靠人工配置，**没有自动读取通道**。

## 8. 复现

```bash
cd 模型

```

六层输出：数据体检 / 假设检验 / 控制器回放 / 反事实闭环 / 消融 / 工况对照。

脚本内 `DATA_DIR` 指向 D 盘数据集，缓存写到 `.cache_old/`（与工作区内
