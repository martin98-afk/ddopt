# 消石灰制备参数控制模型

## 1. 目标与结论

控制**水流量（经水率）**&#x4E0E;**生石灰流量**，维持系统稳定运行：

| 优先级 | 约束 | 取值                            | 依据       |
| --- | -- | ----------------------------- | -------- |
| 1   | 安全 | L1 电流 < X（默认 18A，可设），23A 停产   | 用户指定     |
| 2   | 品质 | L3 出口温度 ∈ [100, 130]℃，目标 118℃ | 控制逻辑.txt |
| 3   | 生产 | 给水给料允许信号 = 1 时才视为生产，才执行控制     | 用户明确要求   |

**核心结论：温度控制已改为趋势预测。** 水率→T3 是滞后负响应（滞后互相关
lag=+20，corr=−0.51），早期事件研究测到的「先升后降」是操作员反馈伪影。
因此控制器不去猜响应形状，而是用「当前温度 + 变化斜率」预测未来、提前干预。

## 2. 数据基础

- 来源：`脱硫脱硝消石灰制备数据/` 下 10 个 zip + 测点清单 CSV
- 跨度：2026-10-12 17:54 ~ 10-19 10:09，9616 分钟
- 生产班次：8 个（2.8~9.2 小时），合计 3079 分钟 / 51.3 小时
- 生产判据校验：允许信号与「生石灰流量 > 0」**完全吻合 3079/3079**

数据为压缩存储（跳变/动态阈值），无记录即代表值未变，故对齐用 step-hold 前向填充。  
这是第一个坑：若按「分钟均值」做，开关量会退化成 311 个 1 分钟孤立点，完全无法识别班次。

## 3. 关键实测发现

### 3.1 水率 → T3 的方向与滞后（决定控制器结构）

严格事件研究，12 个干净的水率阶跃（升 7 / 降 5），相对事件前 15 分钟基线：

| 窗口        | 全部（归一为加水）  | 仅升水率组 | 仅降水率组 |
| --------- | ---------- | ----- | ----- |
| 0~5 min   | **+6.36℃** | +7.05 | −5.38 |
| 5~15 min  | +5.13℃     | +4.71 | −5.72 |
| 15~25 min | −2.51℃     | −2.20 | +2.94 |
| 25~40 min | −3.82℃     | −2.31 | +5.94 |
| 40~60 min | −1.57℃     | −0.33 | +3.30 |

升/降两组符号完全对称，确认是水率驱动，不是巧合。

**推论**：T3 偏高 → 加水。但加水后前 10 分钟 T3 会**再升约 6~7℃**，  
20 分钟后才转为下降。若用常规 PID 连续调节，会在前 10 分钟误判"加水无效"  
而反向操作，或与后续效应叠加造成大幅振荡。

> **2026-10-20 修正：反向期存疑，高度疑似辨识伪影。**
> 质疑成立：加水降温才符合物理（+100L/t ≈ 蒸发吸热 611kW，与反应放热
> 1.1MW 同量级），"先升"更可能是——操作员在 T3 上升途中才加水（反馈
> 行为），滞后窗口内 T3 沿原趋势继续走，事件研究把这段**原趋势延续**
> 误标为加水的正向响应。
> 实测对照（当前宽表仅存 2 个事件）：两事件前 15min T3 均已上升
> （+3.4 / +6.4℃）；加水事件后 0~10min 实测 −0.7℃，并非核声称的先升；
> 核声称 +100L/t 于 5min 内 +46.8℃，输运时间尺度上不成立。
> 影响：①撤下"非最小相位"标签，改为"响应滞后（真实）+ 事件研究
> 伪影（疑似）"；②响应核 G 及 fopdt-dmc 对比实验结论打折——伪影核
> 不能用于预测；③节拍器 / 最小干预 / 无积分的工程决策不变（滞后与
> 不可控扰动真实存在，"等够再评估"对两种机制都稳健）；④Kp 量级
> 待现场受控阶跃重标（点表清单 ③）。

**对策**：旧版用 `action_wait_min = 35 min` 的节拍锁，一次动作后死等超过
稳态效应时间才允许再评估。**该节拍已在趋势控制版本中移除**：滞后负响应
（滞后互相关 lag=+20，corr=−0.51）意味着斜率项能提前捕捉 T3 走向，
节拍锁只会让控制器在 35 分钟内对明显越温无反应。现由 `trend_dead` /
`trend_dead_slope` 承担「无信息不动手」的职责。

### 3.2 水率不是 T3 的主导因素（决定增益取值）

- 稳态段水率标准差仅 **12.7 L/t**，操作员几乎不调
- 但各班次 T3 稳态均值从 108.8 到 137.4℃，跨度 **28.6℃**
- 同步回归斜率 −0.273 ℃/(L/t)，但事件研究幅度仅 ~3.9℃/次典型调节，两者差约 20 倍

**解读**：T3 的班次间差异主要来自原料批次/环境等不可控扰动，水率只能修正一小部分。  
这也解释了为什么历史基线合格率只有 72.6%——不是操作员不努力。

### 3.2b 最小干预的来历：反事实仿真推翻了初版设计（重要）

初版把控制律写成「节拍式 PI，把 T3 死死纠到 118℃」。反事实仿真否掉了它：

| 方案                 | T3 合格率 | 相对人工     |
| ------------------ | ------ | -------- |
| 人工（实际）             | 76.0%  | 基准       |
| 初版 · 节拍式 PI 追 118℃ | 70.7%  | **−5.3** |
| 现行 · 区间守护 + 最小干预   | 75.6%  | −0.4     |

典型病例（10-16 00:04 班次）：

- 人工：水率恒定 630 全程不动 → T3 std 2.9，合格率 100%
- 模型：水率从 630 一路降到 350（物理下限）→ T3 std 9.6，合格率 91%

模型在拼命纠一个它纠不动的量。根因：积分项把不可控扰动的偏差持续累积，  
最终单向漂移触界。**故取消了积分项**。

> 以上是旧「区间守护」版本的历史结论，保留作为设计取舍的依据。
> 现役趋势控制继承了其中两条：无积分、单拍步长有上限（25 L/t）。
> 「最小干预」在趋势控制里的对应物是 `trend_dead`（3℃预测误差死区）
> 与 `trend_dead_slope`（0.3℃/min 斜率死区）。

副产物：水率动作次数降到 0（人工 45 次 / 33.4 小时），  
代价是水率通道在这批数据里从未被触发，其效果无法从仿真验证。

### 3.3 L1 电流：历史从未接近阈值，无法从数据学/tcp

- 生产时段：均值 12.53，标准差 0.36，P99 = 14.11，最大 15.96
- **>18A 占比 0.00%**，>16A 也是 0.00%
- 生石灰流量阶跃 → L1 电流的事件响应在 ±0.1A 内，完全淹没在噪声里

**对策**：电流保护不依赖模型预测，只用「阈值触发 → 阶跃降载 → 观察」的保守规则。  
三级：≥16 预警（禁止增量）、≥18 降载（−0.2 t/h）、≥23 停产。  
X 可配置，改 X 时预警阈值自动跟随下调并保持 2A 余量。

### 3.4 T2 高温是启动期的正常物理现象

实测 T2-2/T2-3 在启动后 20~140 分钟常出现 >200℃ 读数（峰值 422.9℃）。  
现场确认为二级消化器剧烈反应所致，**不是仪表故障**，也不是控制目标。

> 250℃ 的点标记可疑、不参与聚合，但不触发报警。  
> T2-1 全程无 >200℃ 记录，是最干净的二级测点。

### 3.5 启动阶段温度飙升不可用于速率报警

10-14 班次启动后 T3 从 38℃ 升到 150℃，10 分钟变化达 80℃。  
这是物理必然。因此**升温速率保护只在稳态阶段启用**，启动阶段只查硬边界。

若把速率保护放在阶段判定之前（我曾这么写），整个启动阶段会被短路，  
模型永远进不了 STEADY——这是一个已修复的实际 bug。

## 4. 控制架构

```
第 0 层  安全监护（只提示，不停机；停机/联锁由 DCS 决定）
         ├ 料位、联锁、电流、温度边界 → 写入 notes
         └ L1 ≥ 23A：高负荷风险报警（停止制备由 DCS 执行）
第 1 层  阶段判定：微服务模式下由外部判定（双端点）；离线回放内部自动判定
         ├ 启动阶段（POST /startup）：温度同样进趋势闭环 + 电流规则保护
         └ 运行阶段（POST /infer，外部判 T3 ≥ 100℃ 后切换）：温度控制相同，仅端点不同
第 2 层  电流规则（两阶段共用，现场逻辑：水率优先、转速辅助、负荷兑底）
         ├ I1 ≥ X：先加水率（+15 L/t/拍，至上限 690）
         ├ 水率到上限仍高：建议提高一级电机转速（转速现阶段固定输出，仅提示）
         └ 仍高：降下料量（−0.2 t/h/拍）及水率（−5 L/t/拍），下料量限设定值 ±0.5
         电流回落至 X 以下 → 逐拍恢复初始设定（下料 +0.1 / 水 +15）
第 3 层  温度控制 = 趋势预测（启动/运行两阶段一致）
         ├ 预测温度 = T3当前 + 斜率×15min → 偏离目标 118℃ 就调水率
         ├ 双向连续：超标提水率，降回目标且趋势向下则减水回调
         └ 贴目标且平稳（|err|≤ 3℃、|slope|<0.3℃/min）才不动
第 4 层  输出限幅：单拍步长 ≤ 25 L/t（瞬时 >135/<95 时放宽到 60）；
         水率恒裁剪到 [500, 690]；下料量永远在现场设定值 ±0.5 t/h 内
```

**模型输出三个控制值**：水率设定（L/t）、生石灰流量设定（t/h）、
一级电机转速（现阶段固定 46，取实测 42~50 中位，不参与调节）。

**主控制律**（趋势预测控制，模仿人工操作，现役算法）：

```
预测温度 pred = T3当前 + 斜率×15min前瞻
误差       err = pred − 118
步长       = clip(2.0 × err, ±25)   瞬时>135/<95 时上限放宽到 ±60
水率      += 步长                    每拍（10min）可动，双向连续调节
```

- **双向、无死区锁死**：温度超标→提水率；降回目标且趋势向下→减水回调，绝不顶死在一个值
- **提前干预**：斜率（曲率）项让温度还没越线就开始动作
- **响应严重超温**：瞬时 >135/<95 时步长上限放宽到 ±60，当拍触发
- 范围 [500, 690]；下料量 ±0.5 约束不变；电流规则（水率优先→转速辅助→降料兜底）保留
- 参数在 `config.py` ControlParams 的 `trend_*` 组，现场可调

**手段优先级：温度调水率，水率用尽才动给料量**

```
T3 偏离目标 → 水率双向调节（趋势控制，主要手段）
水率已到 690 且 T3 仍偏高 → 电流规则的降料兑底才动给料量（±0.5 内）
```

【当前版本】旧守护带算法（死区 + 35min 节拍 + 顶格锁死）已整体移除，
被趋势预测取代。`config.py` 里相关的旧参数（`temp3_deadband`、
`action_wait_min`、`kp_temp3`、`fast_step_*` 等）仍保留但已无引用，
清理前不影响运行。

【修正记录】初版把降料写在加水之前，且降料触发线 130−8=122 低于  
纠偏触发线 126，数学上导致**加水分支成为死代码**——T3 一旦越过 126  
进入纠偏就必然同时 > 122，直接落到降料。修正后水率动作从 0 次升到  
12 次，降料从 9 次降到 2 次，T3 合格率由 −0.4 转为 **+0.3**。

## 6. 使用

### 6.0 下控准入（先看这个）

**当前不能直接下控。** 软件已就绪（安全合规 0 违规、A/B 转正 +0.3、  
异常输入 6 组全过），但缺三样现场的东西：

| 门槛       | 缺什么         | 为什么数据补不了                  |
| -------- | ----------- | ------------------------- |
| ① 输出通道   | 三个设定值测点是否可写 | 历史库中这些点全为 1970 无效时间戳      |
| ② 电流阈值 X | 电机铭牌额定电流    | 历史电流从未超 16A，保护逻辑从未被真实数据验证 |
| ③ 响应模型   | 现场阶跃测试      | 响应核只有 12 个小幅样本，尾部是外推      |

逐项确认清单见 **`点表确认清单.md`**，拿去现场对照，预计半天。

建议路径：

```
第一步  只查点表，确认三个设定值测点可写          （半天，零风险）
第二步  开环监护：模型只算不发，建议值上 HMI       （2~4 周，零风险）
第三步  闭环水率，给料量保持人工                  （2 周）
第四步  全闭环含电流保护                          （需先完成 ②③）
```

**预期管理**：即使全闭环，T3 合格率也只是与人工持平（+0.3），  
因为主导扰动是原料批次，水率管不了。模型价值在于  
消除班组间操作差异（人工各班次 T3 均值 108.8~137.4℃）与 24 小时安全监护。

### 离线验证

```bash
cd 模型
python backtest.py          # 回放验证，X=18
python test_service.py      # 端到端测试
```

### 在线接入（微服务，推荐）

```bash
cd 模型
python infer.py                              # 读同目录 config.yaml
python infer.py --config my.yaml --port 10030   # 命令行覆盖配置文件
```

所有固定配置集中在 **`config.yaml`**（服务监听 / 现场初始设定 / 时序库地址
与 Bearer 令牌）；`--config` 换文件，命令行参数逐项覆盖，缺字段回落代码默认值。
令牌放在 `tsdb.token`，请求头自动带 `Authorization: Bearer {token}`。

阶段切换由外部判定，两个推理端点各自持续调用：

| 端点           | 阶段     | 行为                                                  |
| ------------ | ------ | --------------------------------------------------- |
| `POST /startup` | 启动阶段 | 初始设定保持；只盯 I1 ≥ X 按现场规则介入；返回体带 T3 供外部判切换（T3 ≥ 100℃ 切运行） |
| `POST /infer`   | 运行阶段 | 趋势预测控制 + 相同电流规则                                          |
| `GET /health`   | —      | 健康检查 + 当前配置 + 末拍输出                                  |
| `POST /reset`   | —      | 重置为未初始化（下次推理惰性重建）                                   |

每次推理从时序库拉实时 9 温度测点 + 一级电流，返回三个控制值：

```json
{
  "ratio_set": 615.0,     // 水率设定 L/t
  "lime_set": 3.30,       // 生石灰流量设定 t/h（限现场设定值 ±0.5）
  "speed_set": 46.0,      // 一级电机转速（现阶段固定，实测中位 46）
  "info": { "phase": "启动", "action": "提高水率", "reason": "…",
            "notes": [], "temp1": .., "temp2": .., "temp3": ..,
            "curr1": .., "lime_band": [3.0, 4.0], "src": "tsdb", "steps": 12 }
}
```

`/startup` 载荷（可选；携带任一初始设定字段即视为新一轮启动，重置历史状态）：

```json
{"ratio_init": 600.0, "lime_sp": 3.0, "curr1_high": 18.0, "speed_set": 46.0}
```

`/infer` 载荷可选：含任一测点字段（`temp1_1`…`temp3_3`、`curr1`）即手动喂数模式，
不访问时序库（离线测试 / 时序库故障兜底）；传 `{}` 走常规时序库拉取。

| ------ | --- |
| 水率越界   | 0   |

**加权平均 T3 合格率 72.6%，与历史基线持平**。

### 7b 反事实 A/B 仿真（6 个班次的稳态段，33.4 小时）

方法：先辨识水率→T3 响应核，再用共同随机数法（双方共用同一扰动序列 d[t]），  
只替换水率操作序列，推演 T3。

| 方案                 | T3 合格率    | 相对人工     |
| ------------------ | --------- | -------- |
| 人工（实际）             | 76.0%     | 基准       |
| 初版 · 节拍式 PI 追 118℃ | 70.7%     | −5.3     |
| 区间守护 + 最小干预（降料优先）  | 75.6%     | −0.4     |
| **现行 · 同上 + 水率优先** | **76.3%** | **+0.3** |

> 130℃ 占比：人工 24.0% → 模型 23.5%；T3 标准差 10.40 → 10.30。

### 7c 手段构成（水率优先后）

| 通道   | 动作次数（33.4h） |
| ---- | ----------- |
| 提高水率 | 11          |
| 降低水率 | 1           |
| 减少给料 | 2           |
| 保持   | 165         |

水率通道从 0 次动作升到 12 次，降料从 9 次降到 2 次，  
5/6 班次完全不降料。水率标准差 19.7（人工 6.6），  
仍在 630±45 操作带内，越界班次 0/6。

**验收标准若为「稳定上线」，模型达标**：不会振荡、不会超调、  
不会把水率推到边界、不会与操作员手动干预打架。

## 8. 已知局限

1. **控制方向的自证无法离线完成**。响应方向靠滞后互相关定符号（lag=+20，
   corr=−0.51），样本量偏弱。真正确认需要现场做阶跃测试：水率阶跃 +50 L/t，
   观察 60 分钟。
2. **水率对 T3 的修正能力有限**（见 3.2）。若原料批次差异导致 T3 系统性偏离，  
   单靠水率无法拉回，需要生石灰流量配合或上游原料管控。
3. **L1 电流保护从未被实测验证**。阈值 16/18/23 是规则而非学到的，  
   实际 X 应结合电机铭牌额定电流重新设定。
4. **仿真是模型内自证**。A/B 在「自己辨识出的响应核」里进行，  
   若 g[k] 有偏，结论就有偏。真实检验仍需现场 A/B：  
   部分班次走模型闭环，部分走人工，对比 T3 合格率与电流峰值。
5. **水率通道样本仍很少**（见 7c）。修正手段优先级后水率动作升到 12 次，  
   但集中在 3 个班次，且这 12 次的实际效果依赖于辨识出的响应核，  
   仍属模型内自证。响应核本身只有 12 个阶跃样本支撑。
6. **给料量对 T3 的影响未建模**。仿真中降料不影响 T3，  
   故「降料降温」这条路目前按无效处理，实际效果未知。
7. **趋势控制的目标 118℃ 与限幅区间按历史分布设定**，未经现场校准。  
   上线后应按实际 T3 分布重新标定 `trend_kp` 与目标值；若希望水率通道更活跃，  
   可缩小 `trend_dead`（当前 3℃）。
8. **水流量可能是独立控制回路**（重要）。实测「水流量」与  
   「水率 × 给料量」的相关系数仅 **+0.672**；给料量变化 28% 时，  
   水流量仅变化 0.1%。说明现场存在独立的水流量控制回路，  
   水流量不由 水率×给料量 决定。

   影响：`service.py` 目前输出 `water_set = ratio_set × lime_set`，  
   这个换算在现场可能不会被实际执行。若水流量可独立设定，  
   应改为直接输出水流量设定值，而非输出「水率」让下游换算。  
   需现场确认 `5#_XSH_SLLSDZ`（水流量设定值）测点是否可写。

9. **水率操作带曾与实测范围不自洽**（已修）。旧 `ratio_band=45`
   推出 `hi=675`，而实测水率最高到 690，导致控制器每分钟都触发
   「水率回归」动作（新数据验证中 46 次降低水率全是这个，与温度无关）。
   已改为 `ratio_band=60`，操作带 [570, 690]。
   回归验证：旧数据上 T3 合格率不变（75.4%），四项安全违规仍为 0。

10. **料位高时会长时间停止制料**。新数据验证中发现生产时段料位
    ≥7.0m 达 406 分钟（占 40%），模型按保护逻辑持续停止给料。
    这是物料平衡问题（下游消耗跟不上制备），非控制缺陷，
    但会影响实际产量，需现场评估。
